## 缺陷管理规范

### 缺陷等级定义

| 等级 | 级别 | 描述 | 处理时限 |
|------|------|------|----------|
| S0 | 致命 | 系统崩溃、数据丢失、核心功能完全不可用 | 立即处理 |
| S1 | 严重 | 核心功能受影响，重要业务无法完成 | 24 小时内 |
| S2 | 一般 | 功能有缺陷但存在绕过方案 | 3 天内 |
| S3 | 轻微 | UI/体验问题，不影响功能使用 | 1 周内 |

### 缺陷状态定义

| 状态 | 说明 |
|------|------|
| 新建 (New) | 缺陷已记录，等待分配 |
| 已分配 (Assigned) | 缺陷已分配给开发人员 |

#### BUG-001：用户密码明文存储，存在安全风险

| 属性 | 内容 |
|------|------|
| **缺陷ID** | BUG-001 |
| **标题** | 用户密码明文存储，存在安全风险 |
| **严重程度** | S1 - 严重 |
| **优先级** | P0 - 最高 |
| **模块** | 用户模块 / 数据库 |
| **创建日期** | 2025-06-01 |
| **创建人** | XXX |
| **指派给** | 后端开发 |
| **当前状态** | 待修复 |

**问题描述**：
用户表中 `password` 字段以明文形式存储，一旦数据库泄露，所有用户密码将直接暴露。这是严重的安全风险，违反信息安全基本要求。

**复现步骤**：
1. 登录 MySQL 数据库
2. 执行 `SELECT user_id, user_name, password FROM wx_user`
3. 查看 password 字段，可以看到明文密码

**预期行为**：
密码应以不可逆加密形式存储（如 BCrypt、MD5+Salt），数据库中无法看到原始密码。

**实际行为**：
当前密码字段直接存储明文，如 `Test@123456`。

**影响范围**：
- 所有已注册用户
- 数据库安全性
- 合规性（个人信息保护）

**修复建议**：
1. 引入 `BCryptPasswordEncoder` 或 `Argon2PasswordEncoder`
2. 注册时：`user.setPassword(encoder.encode(rawPassword))`
3. 登录时：`encoder.matches(rawPassword, dbPassword)`
4. 建议同时引入 JWT Token 认证机制

**相关代码**：
- `User.java` (pojo)
- `UserMapper.java` (selectForLogin)
- `UserServiceImpl.java` (register)

**验证方法**：
1. 注册新用户后查询数据库，password 字段应为加密字符串
2. 使用相同密码再次登录应成功

#### BUG-002：任意 userId 可获取其他用户信息（越权访问）

| 属性 | 内容 |
|------|------|
| **缺陷ID** | BUG-002 |
| **标题** | 任意 userId 可获取其他用户信息（越权访问） |
| **严重程度** | S1 - 严重 |
| **优先级** | P0 - 最高 |
| **模块** | 用户模块 / 安全 |
| **创建日期** | 2025-06-01 |
| **创建人** | XXX |
| **指派给** | 后端开发 |
| **当前状态** | 待修复 |

**问题描述**：
`GET /user/info?userId=xxx` 接口缺少权限校验，任何人只需知道目标用户的 userId，即可查询到该用户的完整信息（包括密码字段），属于典型的越权访问漏洞。

**复现步骤**：
1. 用户 A 登录，获取自己的 userId（如 1）
2. 发送请求：`GET /user/info?userId=2`
3. 即可获取用户 B 的完整信息

**预期行为**：
用户只能查询自己的信息，查询他人信息应返回 403 Forbidden。

**实际行为**：
接口无条件返回目标 userId 对应的用户信息。

**影响范围**：
- 用户隐私信息泄露
- 账户安全风险
- 个人信息保护合规

**修复建议**：
1. 引入 JWT Token 认证
2. 用户登录成功后颁发 Token（包含 userId）
3. 所有用户接口要求携带 Token
4. 后端从 Token 解析 userId，禁止通过参数传递

**相关代码**：
- `UserController.java` (getUserInfo 方法)
- `utils/request.js` (Authorization header)

**验证方法**：
1. 未携带 Token 请求 `/user/info?userId=xxx` 应返回 401
2. 携带他人 userId 的 Token 请求应返回 403

#### BUG-003：订单表缺少 user_id 字段，无法关联用户

| 属性 | 内容 |
|------|------|
| **缺陷ID** | BUG-003 |
| **标题** | 订单表缺少 user_id 字段，无法关联用户 |
| **严重程度** | S2 - 一般 |
| **优先级** | P1 - 高 |
| **模块** | 订单模块 / 数据库 |
| **创建日期** | 2025-06-02 |
| **创建人** | XXX |
| **指派给** | 后端开发 |
| **当前状态** | 修复中 |

**问题描述**：
orders 表缺少 `user_id` 字段，导致无法将订单归属于具体用户。当前所有订单是一个全局列表，无法实现"我的订单"功能。

**复现步骤**：
1. 用户 A 创建订单
2. 用户 B 登录
3. 调用 `GET /order/all`
4. 可以看到用户 A 的订单

**预期行为**：
每个用户只能看到自己创建的订单。

**实际行为**：
所有用户共享同一订单列表。

**修复建议**：
```sql
-- 给 orders 表添加 user_id 字段
ALTER TABLE orders ADD COLUMN user_id BIGINT NOT NULL DEFAULT 0;

-- 添加外键约束
ALTER TABLE orders ADD CONSTRAINT fk_orders_user 
FOREIGN KEY (user_id) REFERENCES wx_user(user_id);

-- 创建订单时写入当前登录用户的 ID
-- 查询订单时强制加上 WHERE user_id = #{currentUserId}
```

**相关代码**：
- `Order.java` (pojo)
- `OrderController.java` (createOrder)
- `OrderServiceImpl.java` (createOrder, getAllOrders)

**验证方法**：
1. 添加字段后，用户 A 创建的订单 user_id 应为 A 的 ID
2. 用户 B 调用 `/order/all` 应只能看到自己的订单

#### BUG-004：商品搜索存在大小写敏感问题

| 属性 | 内容 |
|------|------|
| **缺陷ID** | BUG-004 |
| **标题** | 商品搜索存在大小写敏感问题 |
| **严重程度** | S2 - 一般 |
| **优先级** | P2 - 中 |
| **模块** | 商品模块 |
| **创建日期** | 2025-06-03 |
| **创建人** | XXX |
| **指派给** | 后端开发 |
| **当前状态** | 待修复 |

**问题描述**：
商品搜索时，关键词大小写不同可能导致结果不一致，影响用户体验。

**复现步骤**：
1. 数据库中有课程名称 "Java 基础教程"
2. 搜索 `keyword=java` 返回结果
3. 搜索 `keyword=JAVA` 返回结果可能为空或不同

**预期行为**：
搜索 "java"、"JAVA"、"Java" 应返回相同的搜索结果。

**实际行为**：
根据数据库字符集和 SQL 语句不同，可能存在大小写敏感差异。

**修复建议**：
方案一（推荐，MySQL 层面）：
```sql
-- 查询时统一转小写比较
WHERE LOWER(name) LIKE CONCAT('%', LOWER(?), '%')
```

方案二（应用层面）：
```java
.like("LOWER(name)", keyword.toLowerCase())
```

**相关代码**：
- `ProductMapper.java` (searchProductsByKeyword)
- `ProductServiceImpl.java` (searchProducts)

**验证方法**：
1. 分别用 "java"、"JAVA"、"Java" 搜索，应返回相同结果
2. 用 "PYTHON"、"python"、"Python" 搜索，应返回相同结果

#### BUG-005：重复支付同一订单时无明确提示

| 属性 | 内容 |
|------|------|
| **缺陷ID** | BUG-005 |
| **标题** | 重复支付同一订单时无明确提示 |
| **严重程度** | S2 - 一般 |

| **指派给** | 后端开发 |
| **当前状态** | 待修复 |

**问题描述**：
对于已支付（status=1）的订单，再次调用支付接口时，后端没有明确的错误提示，可能导致用户困惑。

**复现步骤**：
1. 创建订单 A（status=0）
2. 支付订单 A（status=1）
3. 再次点击支付订单 A
4. 查看返回信息

**预期行为**：
返回明确的错误提示："该订单已支付，请勿重复支付"

**实际行为**：
可能返回 success=true（当前）或返回通用错误，无明确业务语义。

**修复建议**：
```java
public boolean payOrder(Long orderId) {
    Order order = getById(orderId);
    if (order == null) {
        throw new BusinessException("订单不存在");
    }
    if (order.getStatus() == 1) {
        throw new BusinessException("该订单已支付，请勿重复支付");
    }
    // 执行支付逻辑...
}
```

**相关代码**：
- `OrderServiceImpl.java` (payOrder 方法)

**验证方法**：
1. 对已支付订单再次调用支付接口
2. 应返回明确提示"该订单已支付"
3. 订单状态应保持为 1，不重复扣款

#### BUG-006：支付成功后订单列表未自动刷新

| 属性 | 内容 |
|------|------|
| **缺陷ID** | BUG-006 |
| **标题** | 支付成功后订单列表未自动刷新 |
| **严重程度** | S3 - 轻微 |
| **优先级** | P2 - 中 |

| **创建人** | XXX |

**问题描述**：
在订单列表页点击支付后，支付成功但页面未自动刷新，用户需要手动切换 Tab 才能看到订单状态更新。

**复现步骤**：
1. 进入"待付款" Tab
2. 点击某一订单的"支付"按钮
3. 支付成功后，页面仍显示在"待付款" Tab
4. 该订单已不在列表中，但用户需要手动刷新才能确认

**预期行为**：
支付成功后，页面应自动刷新订单列表，或自动切换到"已付款" Tab。

**实际行为**：
需要手动切换 Tab 或重新进入页面才能看到最新状态。

**修复建议**：
```javascript
// 在 handlePay 方法中，支付成功后调用
const handlePay = async (orderId) => {
  const res = await put(`/order/${orderId}/pay`, {})
  if (res.success) {
    uni.showToast({ title: '支付成功', icon: 'success' })
    await refreshCurrentTab()  // 刷新当前 Tab
    // 或者主动切换到"已付款" Tab
    // changeTab('paid')
  }
}
```

**相关代码**：
- `pages/purchased/purchased.vue` (handlePay 方法)

**验证方法**：
1. 在"待付款" Tab 下支付订单
2. 页面应自动刷新，订单移至"已付款" Tab

#### BUG-007：API 响应格式不统一

| 属性 | 内容 |
|------|------|
| **缺陷ID** | BUG-007 |
| **标题** | API 响应格式不统一 |
| **严重程度** | S3 - 轻微 |
| **优先级** | P2 - 中 |
| **模块** | 全局 / API |
| **创建日期** | 2025-06-04 |
| **创建人** | XXX |
| **指派给** | 后端开发 |
| **当前状态** | 修复中 |

**问题描述**：
不同模块的 API 响应格式不一致，给前端解析带来困难。

**复现步骤**：
1. 调用 `POST /user/login`
2. 调用 `GET /product/featured`
3. 对比两个接口的响应格式

**当前格式**：
- 用户/订单模块：`{success: true/false, message: "xxx", data: {...}}`
- 商品模块：`{code: 200, message: "success", data: {...}}`

**预期行为**：
所有接口返回统一格式：`{code: 0, message: "success", data: {...}}`

**修复建议**：
定义统一的响应类：
```java
@Data
public class ApiResponse<T> {
    private int code;       // 0=成功，非0=失败
    private String message;
    private T data;
    
    public static <T> ApiResponse<T> success(T data) {
        return new ApiResponse<>(0, "success", data);
    }
    
    public static <T> ApiResponse<T> error(int code, String message) {
        return new ApiResponse<>(code, message, null);
    }
}
```

**相关代码**：
- 所有 Controller 的返回值

**验证方法**：
1. 调用所有 API
2. 检查响应格式是否统一为 `{code, message, data}`
